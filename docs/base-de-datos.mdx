# Base de datos

**Nombre:** `idt_app` · **Motor:** MySQL/MariaDB, tablas InnoDB, charset `utf8mb4`.

El esquema completo (estructura + datos semilla) está en `idt_app.sql` en la
raíz del repositorio.

## Tablas

### `usuarios`

Usuarios del panel administrativo.

| Campo | Tipo | Notas |
|-------|------|-------|
| `ID` | int, PK, autoincrement | |
| `Nombre` | varchar(80) | |
| `Correo` | varchar(80) | login por nombre **o** correo |
| `Foto_Usuario` | varchar(80) | ruta relativa a la imagen de perfil |
| `Funcion` | int, FK → `funciones_usuario.ID` | rol |
| `Password` | varchar(50) | hash **MD5** |

### `funciones_usuario`

Catálogo de roles. Datos semilla: `1 = Administrador`, `2 = Colaborador`.

### `lista-reproduccion`

Programaciones (horarios de contenido).

:::info
El panel ya no tiene una página dedicada para crear/editar programaciones
nuevas (`admin/programacion.php` y afines se eliminaron — ver
[Gestión de contenido](./admin/gestion-de-contenido)). La fila **general**
(`Modulo IS NULL`, la lista "Default") sigue existiendo y sigue siendo el
contenido de respaldo para pantallas sin contenido propio; las filas por
pantalla se siguen creando desde
[`admin/editar_modulo.php`](./admin/gestion-de-contenido#pantallas-modulosphp--editar_modulophp).
:::

| Campo | Notas |
|-------|-------|
| `Nombre` | nombre descriptivo |
| `Modulo` | varchar(150), NULL. Nombre del módulo al que pertenece esta programación (mismo patrón de texto libre que `visitantes.modulo`/`reco.modulo`, sin FK). `NULL`/vacío = programación **general**, visible para todos los módulos que no tengan la suya propia |
| `Fecha-Inicio` | fecha/hora en que debe activarse |
| `Estado` | `1` activo / `0` inactivo — **lo gestiona el sistema automáticamente** en `app/index.php` y `app/activacion.php`, pero **solo entre las programaciones generales** (`Modulo IS NULL OR Modulo = ''`); no se edita a mano en condiciones normales |
| `Fecha-Modificacion`, `Usuario` | auditoría manual |

Solo una programación **general** puede estar `Estado = 1` a la vez. Las
programaciones atadas a un módulo específico no usan `Estado`: se resuelven
por lectura directa (la más reciente con `Fecha-Inicio <= NOW()` para ese
módulo), así que varios módulos pueden tener contenido propio y distinto
**al mismo tiempo**, sin pisarse entre sí ni con el contenido general. Ver
[Flujo del kiosco](./kiosco/resumen-y-flujo#reproducción-de-contenido) para
el orden exacto en que `app/index.php` resuelve esto.

### `contenido`

Cada fila es una **publicación**: un archivo de la
[`biblioteca`](#biblioteca) dentro de una lista de reproducción, con su
orden, estado y ventana de publicación. El mismo archivo puede estar
publicado en varias listas (una fila por lista); dentro de una misma lista
no se duplica (publicarlo de nuevo reprograma la fila existente).

| Campo | Tipo | Notas |
|-------|------|-------|
| `URL` | varchar(255) | nombre del archivo en `admin/assets/galeria/` (mismo valor que `biblioteca.URL`, la relación es por nombre, sin FK) |
| `Tipo` | | `'image'` o `'video'` |
| `Estado` | | `1` activo / `0` inactivo |
| `Orden` | | posición en la reproducción; el kiosco ordena por su valor numérico (`CAST(Orden AS SIGNED)`) |
| `Fecha_Inicio` | datetime, NULL | desde cuándo se muestra. `NULL` = sin límite (desde ya) |
| `Fecha_Fin` | datetime, NULL | hasta cuándo se muestra (exclusivo). `NULL` = sin fin |
| `Lista-Reproduccion` | | FK → `lista-reproduccion.ID` (`ON UPDATE CASCADE`) |
| `Fecha_Modificación`, `Usuario` | | auditoría |

El kiosco solo reproduce las filas con `Estado = 1` y dentro de su ventana
(`Fecha_Inicio IS NULL OR Fecha_Inicio <= ahora` y
`Fecha_Fin IS NULL OR Fecha_Fin > ahora`) — así un contenido se publica y se
retira solo en las fechas programadas (ver
[Sincronización en vivo](./kiosco/resumen-y-flujo#sincronización-en-vivo)).
En el admin, cada publicación se muestra con un estado efectivo:
**Publicado**, **Programado** (aún no llega `Fecha_Inicio`), **Finalizado**
(ya pasó `Fecha_Fin`) o **Inactivo** (`Estado = 0`).

### `biblioteca`

Un registro por archivo subido a `admin/assets/galeria/`, esté publicado o
no. Permite subir contenido sin asignarlo todavía a ninguna pantalla y
reutilizar el mismo archivo en varias. La gestiona
[`admin/contenido.php`](./admin/gestion-de-contenido#contenido-contenidophp).

| Campo | Tipo | Notas |
|-------|------|-------|
| `ID` | int, PK, autoincrement | |
| `URL` | varchar(255), **único** | nombre del archivo en `admin/assets/galeria/` |
| `Tipo` | varchar(10) | `'image'` o `'video'` |
| `Fecha_Subida` | datetime | |
| `Usuario` | varchar(50) | quién lo subió |

`migracion_v5.sql` la crea y la puebla con los archivos que ya estaban
publicados en `contenido` (uno por `URL` distinto). El protector de pantalla
subido desde Configuración **no** se registra aquí.

### `frame`

Tabla de una sola URL que antes definía la página externa del `<iframe>` del
kiosco.

:::info
Ya **no la lee ningún archivo**: `app/frame.php` toma su URL de
`configuracion.URL_Destino` (ver abajo) y el panel tampoco tiene página para
editarla (`admin/frame.php`/`editar_frame.php` se eliminaron). La tabla sigue
existiendo en la base de datos sin ningún efecto.
:::

### `configuracion`

Tiempos de inactividad del kiosco y protector de pantalla, con el mismo
patrón general/específico que `lista-reproduccion.Modulo`: puede haber una
fila **general** (`Modulo IS NULL`) y, opcionalmente, una fila **por
pantalla** que la sobreescribe. La edita
[`admin/editar_configuracion.php`](./admin/gestion-de-contenido#configuración-configuracionphp)
(fila general) o [`admin/editar_modulo.php`](./admin/gestion-de-contenido#pantallas-modulosphp--editar_modulophp)
(fila de una pantalla puntual), y la leen `app/login.php`, `app/registro.php`,
`app/frame.php` (tiempos y URL de destino) y `app/index.php` (protector y
URL de destino).

| Campo | Tipo | Notas |
|-------|------|-------|
| `ID` | int, PK, autoincrement | |
| `Modulo` | varchar(150), NULL | `NULL` = configuración **general** (fallback); con un nombre de pantalla = override específico de esa pantalla |
| `Tiempo_Inactividad_Kiosco` | int, default `60` | segundos de inactividad en `login.php`/`registro.php` antes de volver a `index.php` (`Inactividad1.js`) |
| `Tiempo_Inactividad_Contenido` | int, default `900` | segundos de inactividad en `frame.php` antes de volver a `index.php` (`Inactividad2.js`) |
| `Protector_URL` | varchar(150), default `IDT.mp4` | nombre del archivo en `admin/assets/galeria/` (mismo folder que usa `contenido.php`, no una carpeta aparte) |
| `Protector_Tipo` | varchar(10), default `video` | `'video'` o `'image'` |
| `URL_Destino` | varchar(255), default `''` | URL externa a la que navega el kiosco cuando el visitante toca la pantalla (se muestra en `app/frame.php` vía `proxy.php`). Vacío = sin configurar: el toque no hace nada. En una fila de pantalla, vacío al guardar toma el valor de la general |
| `Fecha-Modificacion`, `Usuario` | | auditoría manual |

Todas las páginas que leen `configuracion` resuelven primero la fila
específica de la pantalla actual (`Modulo` = su nombre) y, si no existe,
caen a la fila general (`Modulo IS NULL`).

`Protector_URL`/`Protector_Tipo` (de la fila que corresponda) son el
contenido que `app/index.php` reproduce como protector de pantalla mientras
nadie ha tocado — antes era el archivo fijo `assets/media/IDT.mp4`, ahora es
configurable desde el admin.

### `eventos_pantalla`

Un registro por cada evento de uso de una pantalla (hoy, un solo tipo:
`SCREEN_STARTED`, cuando un visitante toca el protector de pantalla). Lo
inserta `app/registrar_evento.php` y lo consume
[`admin/reporte_pantallas.php`](./admin/usuarios-roles-y-reportes#reportes-solo-administrador).

| Campo | Tipo | Notas |
|-------|------|-------|
| `ID` | int, PK, autoincrement | |
| `Modulo` | varchar(150) | nombre de la pantalla (`$_SESSION['modulo']`), texto libre igual que `lista-reproduccion.Modulo` |
| `Evento` | varchar(50) | p. ej. `SCREEN_STARTED` |
| `Fecha_Hora` | datetime | |

### `modulos`

Los kioscos/pantallas físicas registradas (nombre + ubicación). Es lo que se
elige en `app/log_index.php` al configurar cada pedestal, y lo que gestiona
[`admin/editar_modulo.php`](./admin/gestion-de-contenido#pantallas-modulosphp--editar_modulophp)
como centro de administración de cada pantalla (contenido propio, protector
propio, URL estable `app/index.php?pantalla=<ID>`).

### `visitantes`

Historial de personas que se registraron en un kiosco (tipo y número de
documento, nombres, apellidos, módulo, fecha de ingreso).

### `reco`

Estadísticas de uso (edad, género, tiempo, expresión) capturadas por un
sistema externo de reconocimiento — **sin página activa que la consuma hoy**
(ver [Arquitectura](./arquitectura#archivos-muertos-conocidos)).

## Relaciones

```
funciones_usuario 1───N usuarios

lista-reproduccion 1───N contenido

biblioteca 1───N contenido   (por nombre: contenido.URL = biblioteca.URL, sin FK)

modulos, frame, configuracion, visitantes, reco, eventos_pantalla →
tablas independientes, no por llave foránea. lista-reproduccion.Modulo,
configuracion.Modulo, visitantes.modulo, reco.modulo y
eventos_pantalla.Modulo se relacionan con modulos.nombre_modulo por
convención (nombre de módulo/pantalla como texto), no por llave foránea.
```

## Notas de diseño a tener presente

- Los nombres de columnas usan **guiones** en algunos casos (`Lista-Reproduccion`,
  `Fecha-Inicio`, `Fecha-Modificacion`) — en SQL van entre backticks. Es
  inconsistente con el resto (que usa guion bajo o nada), pero así está en
  producción; no se ha normalizado para no romper consultas existentes.
- No hay llaves foráneas para `modulos`/`frame`/`visitantes` — la integridad
  referencial ahí depende de la aplicación, no de la base de datos.
